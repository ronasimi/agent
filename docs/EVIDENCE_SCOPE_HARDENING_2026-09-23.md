# Evidence Scope and Reuse Hardening — 2026-09-23

## Problem

A generic weather follow-up such as `what is the current weather?` could be parsed as though the phrase `what is the` were a location. Because prior weather observations were eligible for fresh stored reuse, generic request words could also satisfy the old scope matcher. The fact ledger could therefore report weather as satisfied while the deterministic weather renderer had no current normalized payload to render.

This created a split-brain state: grounding was satisfied, but completion was not renderable.

## Fixes

### Weather scope parsing

- Generic and interrogative weather phrases are rejected as location candidates.
- Generic follow-ups inherit the previous weather location when available.
- Otherwise the configured/profile default location is used.
- Referential follow-ups such as `And Toronto?` still switch location.
- Time-only follow-ups such as `What about tomorrow?` retain location and change time scope.

### Grounding scope verification

- Weather location matching now uses location-bearing tokens only.
- Generic words such as `what`, `weather`, `forecast`, `current`, and `now` cannot establish location scope.
- Explicit caller-supplied fact frames remain authoritative instead of being silently regenerated by the grounding validator.

### Evidence provenance and hydration

- Every successfully grounded fact now identifies a concrete selected evidence record.
- Satisfied fact requirements retain evidence provenance.
- Stored weather evidence retains its exact durable observation reference.
- Fresh or stored structured weather observations can be normalized back into the deterministic weather formatter.
- If a fact is marked grounded but its deterministic payload cannot be hydrated/rendered, the fact is reopened and retrieval runs again instead of falling through with an unusable satisfied state.

### Working-state retention

- `stored:` evidence references now pin their underlying observation tool in bounded working-state evidence retention.
- Recipe-stage requirement satisfaction now records an evidence preview rather than closing requirements without provenance.

## Cross-domain audit

The grounding validator was audited across:

- current time
- encyclopedic facts
- host state
- network state
- repository state
- news
- market prices
- generic web facts
- weather

Every successful grounding decision is now required by regression tests to expose concrete selected evidence metadata. Automatic cross-turn stored fact reuse remains limited to weather; other live fact paths require current-turn evidence unless reuse is explicitly requested.

## Completion invariant

For deterministic fact flows, a fact may not remain effectively complete if the corresponding evidence cannot be rendered or consumed. The runtime must either:

1. hydrate and render the selected evidence, or
2. reopen the requirement and retrieve fresh evidence.

This prevents `satisfied` ledger state from diverging from usable completion state.
